# Голоса ElevenLabs: кого использовать для генерации

Кастинг реплик номера. Записано, чтобы при следующей генерации на
[elevenlabs.io](https://elevenlabs.io) не подбирать голоса заново и не получить
персонажа, который звучит иначе, чем в уже готовых файлах.

Тексты реплик — в [scenario/CLAUDE_HANDOFF_LOHEN_AUDIO_PROJECT.md](../scenario/CLAUDE_HANDOFF_LOHEN_AUDIO_PROJECT.md).
Куда класть готовые файлы — [README, раздел 3](../README.md).

Теги в квадратных скобках — указания подачи для модели v3. Они заметно влияют на

`projecting to a large hall`, а у Serafina — самой тихой из-за `quietly`. Если
генерировать остальные реплики без тегов, баланс между персонажами не совпадёт с
уже готовыми файлами.

## Генерация через MCP: что нужно знать

С 2026-07-30 подключён MCP-сервер ElevenLabs, поэтому реплики генерируются из
проекта, без ручной выгрузки и нарезки. Четыре находки, которые стоит помнить.

**1. Free не даёт библиотечные голоса через API.** Жёсткий отказ, символы не
списываются:

```text
402 paid_plan_required
Free users cannot use library voices via the API.
```

В веб-интерфейсе те же голоса на free работают — так и получились три первые
реплики. Для генерации из проекта нужен любой платный тариф; оформлен Creator.

**2. `pcm_24000` доступен и без Pro.** В документации тариф оговорён только для
PCM 44.1 кГц, который требует Pro за $99. Формат 24 кГц — сырой PCM без потерь,
полоса до 12 кГц. Для речи под фоном зала этого более чем достаточно, так что Pro
проекту не нужен.

**3. Сервер называет всё `.mp3` и не пишет заголовок.** Файл с `pcm_24000` внутри
— headerless `s16le`, ни MPEG-фреймов, ни RIFF. FFmpeg его не опознает, формат
надо задавать вручную:

```bash
ffmpeg -f s16le -ar 24000 -ch_layout mono -i tts_xxx.mp3 ...
```

**4. Пик приходит около 0 dBFS.** У четырёх новых реплик от −0.31 до −7.70 dBFS.
Голосовым событиям обязателен `normalize_source`, иначе они уронят громкость всей
дорожки — см. раздел про уровни ниже.

## Звуковые эффекты: две находки 2026-07-30

Сгенерированы `ice_burst`, `fabric_drop` (`text_to_sound_effects`) и `ice_drone`
(`compose_music`, `force_instrumental`). Полный разбор — в точке состояния
[v3c](status/2026-07-30-v3c.md) §3 и §4.

**1. Атака может стоять не в начале файла, и это надо проверять замером.**
У первого дубля `ice_burst` перед треском оказалось **130 мс плавного разгона** с
−40 до −28 dB. `trim_silence` его не срезает: это не тишина, а тихое содержание.
Событие стояло в 00:49.600, а треск приходил на 49.830 — на 230 мс позже движения
исполнителя.

Проверять надо огибающей по первым 300 мс, а не на слух и не по длительности:

```bash
ffmpeg -v error -y -t 0.3 -i new.wav -f s16le -ac 1 -ar 48000 head.raw
```

Для сравнения, правильный одиночный удар (`ice_final_impact`) даёт −1.3 dB в
первом же блоке 50 мс.

Просьба «starts instantly with no build-up» помогает, но не бесплатно: второй
дубль атаковал с нуля, зато его тело вышло на 8 dB тише. Надёжнее взять сильный
дубль и срезать разгон вручную, сохранив исходник в `archive/`.

**2. Формат: `opus_48000_192`, а не `pcm_24000`.** Последний без потерь, но режет
всё выше 12 кГц, а у ледяных ассетов там живёт весь треск — у `ice_final_impact`
RMS выше 13 кГц −28.3 dB против −9.7 по всей полосе. Opus 48 кГц даёт полную
полосу и родную частоту проекта, без пересемплирования. На 192 кбит/с потери для
эффектов неощутимы, а срез на 12 кГц ощутим точно.

Правило «не использовать MP3 как источник мастера» касается мастер-файла, а не
генерации ассетов.

**3. `text_to_sound_effects` жёстко ограничен 5 секундами.** Для протяжённых слоёв
нужен `compose_music` (3000–600000 мс), у него параметра формата нет — отдаёт mp3.
Для низкого дрона это безразлично, вся энергия ниже 1 кГц.

## Как переносить результат в проект

Если генерация всё же идёт через веб-интерфейс, порядок такой.

**1. Экспорт.** ElevenLabs отдаёт MP3 128 kbps, моно, 44.1 кГц. Это потери, а
голоса несут весь номер — через API берите `pcm_24000`, он без потерь и доступен
на любом тарифе.

**2. Один файл на всю сессию.** При нескольких спикерах выгружается **один**
файл, названный по одному из голосов — в нашем случае по Christian, хотя внутри
три разных голоса. По имени файла содержимое определить нельзя, надо смотреть
саму сессию.

**3. Разрезать на события.** Сценарий ждёт по одному файлу на событие с точными
именами. Блоки внутри выгрузки разделены **настоящей цифровой тишиной** около
−85 dB, тогда как паузы внутри реплики — это фон около −45 dB. Поэтому границы
надёжно ищутся так:

```bash
ffmpeg -hide_banner -i session.mp3 -af "silencedetect=noise=-60dB:d=0.25" -f null -
```

Паузы длиннее 0.4 с между блоками — границы реплик; более короткие принадлежат
самой реплике и разрезать по ним нельзя.

**4. Формат под проект.** Остальные ассеты — 48 кГц, стерео, `pcm_s16le`.
Приведение выглядит так (границы подставить свои):

```bash
ffmpeg -y -i session.mp3 -af "atrim=start=8.300:end=13.557,asetpts=PTS-STARTPTS,aresample=48000:first_pts=0,aformat=sample_fmts=fltp:sample_rates=48000:channel_layouts=stereo,afade=t=in:st=0:d=0.008:curve=tri,afade=t=out:st=5.249:d=0.008:curve=tri" -ar 48000 -ac 2 -c:a pcm_s16le assets/voices/lohen_notice.wav
```

Фейды 8 мс по краям — против щелчков на стыках. Перевод моно в стерео забирает
около 3 dB: FFmpeg сохраняет суммарную мощность, а не уровень канала. Это не
потеря, но пики готовых файлов окажутся ниже, чем у исходного MP3.

## Уровни: что учесть

Ловушка сработала и была исправлена. Изначально голосовые события, в отличие от
всех 20 событий `sfx`, не имели ни `normalize_source`, ни `gain_db` — файл
попадал в микс с коэффициентом 1.0, и пик реплики съедал запас, из которого
`loudnorm` берёт линейный прирост.

| | LUFS | Crest | Прирост |
|---|---|---|---|
| Без голосов | −18.4 | 16.4 | +8.5 |
| 3 голоса с коэффициентом 1.0 | **−20.0** | 17.6 | **+1.8** |
| 3 голоса с `normalize_source` | −17.4 | 15.0 | +7.28 |
| 7 голосов с `normalize_source` | **−16.7** | 14.4 | +6.98 |

Вторая строка — дорожка стала **тише**, чем была вообще без голосов. Теперь
`normalize_source: true` стоит у всех семи событий, реплики выходят на −9.60 dBFS
(это `mix.absolute_headroom_db`), то есть на 4 dB выше самого громкого акцента —
иерархия §10 соблюдена. `gain_db` не понадобился: при нулевом смещении баланс уже
верный.

Что стоит держать в голове при следующих генерациях: `normalize_source`
выравнивает **по пику**, а не по громкости. Реплика, произнесённая плотно и ровно,
окажется субъективно громче реплики с выраженными пиками при том же значении.
Пример — `lohen_final_question`: пик всего −7.70 dBFS, но RMS −16.44, самый
высокий из четырёх. Замер этого не покажет, только ухо.
