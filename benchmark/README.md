# Бенчмарк нарезки аудио

Меряет, сколько на данной машине занимает нарезка аудиофайлов через FFmpeg и
стадии, из которых состоит сборка дорожки в `src/`. Нужен для двух вещей:
сравнить производительность разных компьютеров и увидеть, куда на самом деле
уходит время.

Зависимостей нет: Python 3.11+ из стандартной библиотеки и `ffmpeg` в PATH —
то же требование, что у основного проекта.

## Запуск

```bash
python benchmark/bench.py
```

Полный прогон занимает около 40 секунд. Результаты появятся в
`benchmark/results/` — двумя файлами: `<метка>.json` для сравнения и
`<метка>.md` для чтения.

Метка по умолчанию — имя хоста. На второй машине удобно задать её явно, чтобы
файлы не перепутались:

```bash
python benchmark/bench.py --label work-laptop
```

Другие ключи:

| Ключ | Что делает |
|---|---|
| `--quick` | 2 повтора без прогрева, примерно 8 секунд — для проверки, что всё работает |
| `--repeats N` | повторов на случай (по умолчанию 5) |
| `--workers N` | потоков в параллельном случае (по умолчанию — число ядер) |
| `--regen` | перегенерировать исходники в `.work/sources` |
| `--keep-work` | не удалять срезы после прогона |
| `--compare` | не мерить, а показать все готовые JSON рядом |

## Сравнение двух машин

Снимите результаты на обеих, положите оба JSON в `benchmark/results/` (через
git это происходит само) и запустите:

```bash
python benchmark/bench.py --compare
```

Выведется таблица «случай × машина» с минимальным временем и отношением к
первой машине по алфавиту.

## Что именно меряется

**Накладные расходы**

* `startup` — пустой `ffmpeg -version`. Работы нет, меряется только стоимость
  создания процесса. Это опорное число для всего остального.

**Нарезка аудио**

* `slice_copy` — один срез 1.5 с через `-ss`/`-t` и `-c copy`, без
  перекодирования.
* `slice_encode` — тот же срез с перекодированием в `pcm_s24le`.
* `slice_atrim` — тот же срез фильтром `atrim`; так режет настоящая сборка.
* `slice_batch_separate` — 20 срезов как 20 отдельных вызовов ffmpeg,
  последовательно.
* `slice_batch_single` — те же 20 срезов одним вызовом: `asplit` и по `atrim`
  на каждый выход.
* `slice_batch_parallel` — те же 20 отдельных вызовов, но в пуле потоков по
  числу ядер. Потоки годятся, потому что `subprocess.run` отпускает GIL на всё
  время ожидания ffmpeg.

Три последних случая отвечают на главный вопрос: сколько в партии срезов
занимает обработка, а сколько — повторный запуск процесса.

**Стадии конвейера сборки**

Повторяют то, что делает `src/renderer.py`, чтобы числа переносились на
реальную сборку: `silence_edges` (замер тишины по краям), `peak_astats` (замер
пика), `volume_envelope` (`volume` с `eval=frame` на всей длине),
`mix_amix` (микс 8 событий с огибающими), `loudnorm_analyze` (проход
измерения громкости).

## Методика

* Исходники **не берутся из `assets/`** — они генерируются самим ffmpeg из
  `sine` и `anoisesrc` с фиксированным сидом. Материал на любой машине
  одинаковый, бенчмарк работает на свежем клоне, ассеты не нужны.
* Длинный исходник — 103 с, ровно `total_duration` сценария. Короткий — 3 с,
  типичный one-shot. Формат тот же, что у сборки: 48 кГц, стерео, 24 бита.
* Перед замерами идёт прогревочный прогон — он греет кэш файловой системы и в
  результат не попадает.
* **Для сравнения машин берите минимум**, а не среднее: минимум меньше всего
  искажён посторонней нагрузкой. Столбец «разброс» показывает, насколько
  медиана ушла от минимума; если он больше 15–20%, машина была чем-то занята и
  прогон стоит повторить.
* Время принципиально не детерминировано — в отличие от самой сборки, которая
  на одинаковом входе даёт одинаковый выход.

Чтобы сравнение было честным, снимайте результат на незанятой машине: закройте
тяжёлые приложения, дождитесь конца индексации, не запускайте бенчмарк на
батарее в режиме энергосбережения.

## Про GPU

Варианта «на GPU» здесь нет намеренно. В FFmpeg **нет** аудиофильтров с
аппаратным ускорением — все методы из `ffmpeg -hwaccels` (cuda, qsv, vaapi,
d3d11va, opencl, vulkan) относятся только к видео. Проверяется одной командой:

```bash
ffmpeg -hide_banner -filters | grep -iE "cuda|opencl|vulkan|qsv" | grep -E "A+->A+"
```

Пустой вывод — ни один аудиофильтр GPU не использует.

Кроме того, ускорять здесь почти нечего: 103 с стерео 48 кГц — это около 10
миллионов сэмплов, то есть десятки миллионов операций на весь микс. Перенос
таких объёмов через PCIe стоит дороже самого счёта. А самая медленная стадия,
`loudnorm`, — это скользящее окно с состоянием (гейтинг EBU R128), которое
принципиально последовательно.

Реальный резерв — в другом, и бенчмарк это показывает числами: убрать
повторные запуски процесса (кэшировать замеры исходников, объединять вызовы) и
распараллелить независимые вызовы.

## Заметка о приватности

В `results/*.json` и `*.md` попадает имя хоста, модель процессора и версия ОС —
это нужно, чтобы отличать машины друг от друга. Если такие данные не должны
попасть в публичный репозиторий, задавайте `--label` и подчищайте секцию
`environment` перед коммитом.
